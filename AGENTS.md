# AGENTS.md

This project is a website built with Edge Delivery Services in Adobe Experience Manager Sites as a Cloud Service. As an agent, follow the instructions in this file to deliver code based on Adobe's standards for fast, easy-to-author, and maintainable web experiences.

## Project Overview

This project is based on the https://github.com/adobe-rnd/aem-boilerplate-xwalk/ project and set up as a new project. You are expected to follow the coding style and practices established in the boilerplate, but add functionality according to the needs of the site currently developed.

The repository provides the basic structure, blocks, and configuration needed to run a complete site with `*.aem.live` as the backend.

### Key Technologies
- Edge Delivery Services for AEM Sites (documentation at https://www.aem.live/ – search with `site:www.aem.live` to restrict web search results)
- Vanilla JavaScript (ES6+), no transpiling, no build steps
- CSS3 with modern features, no Tailwind or other CSS frameworks
- HTML5 semantic markup generated by the aem.live backend, decorated by our code
- Node.js tooling

## Setup Commands

- Install dependencies: `npm install`
- Start local development: `npx -y @adobe/aem-cli up --no-open --forward-browser-logs` (run in background, if possible)
  - Install the AEM CLI globally by running `npm install -g @adobe/aem-cli` then `aem up` is equivalent to the command above
  - The dev server runs at `http://localhost:3000` with auto-reload. Open it in playwright, puppeteer, or a browser. If none are available, ask the human to open it and give feedback.
- Run linting before committing: `npm run lint`
- Run the unit tests: `npm test` (Node's test runner, `test/**/*.test.mjs`; pure modules such as `blocks/list/list-data.js`)
- Auto-Fix linting issues: `npm run lint:fix`

## Code Style Guidelines

### JavaScript
- Use ES6+ features (arrow functions, destructuring, etc.)
- Follow Airbnb ESLint rules (already configured)
- Always include `.js` file extensions in imports
- Use Unix line endings (LF)

### CSS
- Follow Stylelint standard configuration
- Use modern CSS features (CSS Grid, Flexbox, CSS Custom Properties)
- Maintain responsive design principles
  - Declare styles mobile first, use `min-width` media queries at 600px/900px/1200px for tablet and desktop
- Use `rem` for all sizes (1rem = 16px; at most 4 decimals), not `px` or `em`; only the media query breakpoints stay in px
  - Letter-spacing and other font-relative values are derived from the rule's font size, e.g. `letter-spacing: calc(-0.02 * var(--heading-font-size-l))` or `-0.06rem` for a 3rem title. Where a rule resizes an element (a heading, button or tag), set its letter-spacing for the new size too
- Ensure all selectors are scoped to the block.
  - Bad: `.item-list`
  - Good: `.{blockname} .item-list`   
- Avoid classes `{blockname}-container` and `{blockname}-wrapper` as those are used on sections and could be confusing.

### HTML
- Use semantic HTML5 elements
- Ensure accessibility standards (ARIA labels, proper heading hierarchy)
- Follow AEM markup conventions for blocks and sections

## Key Concepts

### Content

CMS authored content is a key part of every AEM Website. The content of a page is broken into sections. Sections can have default content (text, headings, links, etc.) as well as content in blocks.

If no authored content exists to test against, you can create static HTML files in a `drafts/` folder at the project root. Pass `--html-folder drafts` when starting the dev server. Follow the aem markup structure and save files with `.html` or `.plain.html` extensions.

Background on content and markup structure can be found at https://www.aem.live/developer/markup-sections-blocks and https://www.aem.live/developer/markup-reference respectively.

You can inspect the contents of any page with `curl http://localhost:3000/path/to/page`, `curl http://localhost:3000/path/to/page.md`, and `curl http://localhost:3000/path/to/page.plain.html`

### Content Modeling

Modeling the content for blocks and sections must follow the best practices on https://www.aem.live/developer/component-model-definitions

After making changes to the models in partial files (`_{blockname}` for example) run `npm run build:json` to regenerate the arragated files definitions, models and filters.

Use `npm run lint` to verify the models follow the best practices. You can refer to https://github.com/adobe-rnd/eslint-plugin-xwalk?tab=readme-ov-file#rules for more details about the applied rules.

Remember, building semantically appealing block, section and document models is key to  built websites with Edge Delivery Services in Adobe Experience Manager Sites as a Cloud Service using Universal Editor.

You can find plenty of examples, also for complex use cases, on GitHub https://github.com/adobe-rnd/aem-boilerplate-xwalk/pulls?q=is%3Aopen+is%3Apr+label%3AExample

### Blocks

Blocks are the re-usable building blocks of AEM. Blocks add styling and functionality to content. Each block has an initial content structure it expects, and transforms the html in the block using DOM APIs to render a final structure. 

The initial content structure is important because it impacts how the author will create the content and how you will write your code to decorate it. In some sense, you can think of this structure as the contract for your block between the author and the developer. You should decide on this initial structure before writing any code, and be careful when making changes to code that makes assumptions about that structure as it could break existing pages.

The block javascript should export a default function which is called to perform the block decoration:

```
/**
 * loads and decorates the block
 * @param {Element} block The block element
 */
export default async function decorate(block) {
  // 1. Load dependencies
  // 2. Extract configuration, if applicable
  // 3. Transform DOM
  // 4. Add event listeners
}
```

Use `curl` and `console.log` to inspect the HTML delivered by the backend and the DOM nodes to be decorated before making assumptions. Remember that authors may omit or add fields to a block, so your code must handle this gracefully.

Each block should be self-contained and re-useable, with CSS and JS files following the naming convention: `blockname.css`, `blockname.js`. Blocks should be responsive and accessible by default.

**Additional tab.** Every block model except header and footer ends with an "Additional" tab: Anchor ID (`classes_anchor`, must start with `anchor-`, e.g. `anchor-our-services`), Hide block (`classes_hideblock`) and Padding / Margin Left, Right, Top, Bottom (`classes_padding*` / `classes_margin*`, the `--space-*` tokens in rem: `pt-400` = `var(--space-400)`). They are `classes_*` fields, so they arrive as block classes and never shift the rows of positional blocks. `decorators/block-options-decorator.js` makes the anchor class the block's id (de-duplicated with `-2`, `-3`, ...); `styles/styles.css` hides `hideblock` blocks on the page (dimmed and outlined in Universal Editor) and applies the spacing classes. Add the same tab to new blocks (copy it from an existing `_block.json`; `max-cells` allows 8 for the tab fields).

**Data layer.** Every block is in the Adobe Client Data Layer (`window.adobeDataLayer`, Core Components schema) for Adobe Tags and the Web SDK: `decorators/data-layer-decorator.js` adds the page and the blocks and captures clicks, show / hide, media, search, submit and change events centrally (see decorators/README.md). Blocks don't push clicks themselves; they describe them with `data-cmp-interaction`, `data-cmp-value`, `data-cmp-position` and `data-cmp-id`, and push only state the central code can't know (`pushComponentEvent` from `utils/analytics.js`, e.g. a tab or slide shown).

**Accessibility.** Blocks meet WCAG 2.1 AA: buttons are `<button>`s with `aria-expanded` / `aria-controls` for disclosures, Escape closes popups and returns focus, moving content (Lottie, background video) has a pause / play button, links opening a new tab say so (`announceNewTab`), form errors are shown next to their field and linked with `aria-describedby`, and all UI text comes from placeholders.

### Shared code: decorators and utils

Blocks don't re-implement shared behavior; they import it from single-purpose modules:

- `decorators/` create or decorate elements: buttons (`button-decorator.js`, `icon-button-decorator.js`, `content-buttons-decorator.js`), links, headings, content, images, dates, tags, media players and accessibility helpers. Every button and link button goes through the button decorators.
- `utils/` are helpers that build no UI: block properties, multifields, links, dates, tags, URLs, ids, environment / viewport checks, media URLs, Lottie, page metadata, placeholders and taxonomy.
- Decorators may import utils; utils never import decorators. Keep one purpose per file and add new shared behavior there, not in a block. Each folder's README lists its modules, exports and users.

```
/content/tcs-corp/
├── us/en/                  # a locale site (country/language), published at /en/; the other 13 follow the same layout
│   ├── (the locale page)   # Home: the locale page itself (us/en), published at /en/
│   ├── …                   # the content pages
│   ├── references/         # nav (header), footer and other fragments / reference pages
│   ├── error-pages/        # 404 (used by 404.html); 403 / 500 are for the CDN, not used by code

│   ├── placeholders        # sheet: Key, Text, Description, Category
│   ├── metadata            # sheet: bulk metadata (columns below)
│   ├── taxonomy            # taxonomy page (tag, title; a sheet per language for translations)
```

| Templates | The Page Type page property, else the metadata sheet's `page-type` | `scripts.js` `loadTemplate` loads `templates/{name}/{name}.js|css` (see templates/README.md) |
| Error pages (404) | Authorable and inherited like Navigation / Footer: the **404 Page** (`error-page`) page property of the missing page's nearest parent page up to Home (or the metadata sheet's `error-page` column), else the locale's `/{locale}/error-pages/404`, else `/en/error-pages/404`, else the built-in content; a page that fails to load falls through to the next | `scripts.js` `loadErrorPage` in `404.html` (with `getInheritedMetadata('error-page')`); content from another locale is marked with its `lang`. 403 / 500 aren't served by Edge Delivery; a CDN can serve the authored pages |
| Page metadata | Page properties and the locale's bulk metadata sheet (`/en/metadata.json`, `/de-de/metadata.json`, ...; applied once listed in the site configuration's `metadata.source`) | `utils/metadata.js` (`getPageMetadata`, `getPageTags`, `getPageLanguage`); `decorators/seo-decorator.js` applies the SEO / social columns and `<html lang>`; Page Type becomes a body class |

| Redirects | `/{locale}/redirects.json` per locale | none; the platform only applies a root `/redirects.json`, so these sheets need another mechanism (e.g. CDN rules) |

Bulk metadata columns: `url`, `page-type`, `meta-title`, `meta-description`, `meta-keywords`, `author-id`, `publish-date`, `modified-date`, `reading-time`, `og-title`, `og-description`, `og-image`, `og-type`, `twitter-card`, `twitter-title`, `twitter-description`, `twitter-image`, `canonical-url`, `robots`, `region`, `country`, `language`, `persona`, `thumbnail-image`, `featured-image`, `campaign-id`, `content-type`, `featured`, `priority`, `listen-link`, `author`, `card-title`, `card-description`, `card-image`, `card-image-alt`, `image-alt`, `eyebrow`, `category`, `hide-in-nav`. Each column is published as `<meta name="{column}">`; the SEO decorator maps meta-title, meta-description, meta-keywords, og-*, twitter-* and canonical-url to the standard tags in the browser (`robots` is standard and works server side). The Page Header takes all its content from metadata: page-type (default layout), title, description, tags, content-type (eyebrow / label), publish-date, reading-time, author-id (Authors sheet: name, designation, region, image, LinkedIn), featured-image (Landing) and listen-link (listen action; share and download come from code); only its Layout and CTA List are authored. The List block (`blocks/list`, see its README) lists child pages, a fixed list (List Items) or tagged pages from the query index, as cards from card-title, card-description, card-image, card-image-alt, eyebrow / category, tags, content-type and the dates (pages with hide-in-nav = yes are left out; links go to the redirect targets of `/{locale}/redirects.json`), with grid or horizontal scroll per breakpoint. The Cards block (`blocks/cards`, see its README) is its manual authoring alternative: each Card holds its own image, eyebrow, title, rich text description, label, tags, date, link and call to action, with the List's presentation and block settings (shared: `models/_card-list.json` fields, `utils/card-list-config.js`, `decorators/card-list-decorator.js`, `styles/card-list.css`). The Filter List lists the locale's pages from the query index (`utils/query-index.js`, loaded once) below its Root path, of its Page types (page-type) and Content types (content-type), or a manual list, in its Sort order; its filter pills are curated tags (labels from the taxonomy), its advanced filter the tags below taxonomy roots. Cards are built from the metadata columns of its Card mapping (featured-image, else thumbnail-image; content-type; title; description; tags with reading-time; path; author, else author-id from the Authors sheet) with publish-date; the hero and featured spotlight cards come from featured (yes / true) and priority (featured cards: featured, else priority <= 3); `feature-card` / `featured-priority` are read as fallbacks; the footer lists the Social Links sheet in sort-order.

Notes:
- `paths.json` (generated by `npm run build:paths`; 154 mappings; applied to the site configuration's `public.json` → `paths`, which AEM uses instead of the repository file): one mapping per locale folder (`/content/tcs-corp/de/de-de/:/de-de/`), then one per locale Home page (`/content/tcs-corp/de/de-de:/de-de/`: the locale page itself is published as `/de-de/index`; after the folder mappings so `/de-de/index` resolves to it), then, per locale, one per sheet — `placeholders`, `metadata`, `redirects`, `data/authors`, `data/locations`, `data/partners`, `data/social-links`, `data/media-contacts` (e.g. `/content/tcs-corp/de/de-de/data/authors:/de-de/data/authors`; spreadsheets get `.json` appended) — and the taxonomy page (`…/taxonomy:/de-de/taxonomy.json`). `includes` lists the 14 locale pages (`/content/tcs-corp/de/de-de`, covering the page and everything below it); `excludes` the 14 block libraries and `site-global-templates` (author only). Pages outside the locales (e.g. `/content/tcs-corp` itself) aren't published, so `/` needs a redirect to `/en/` (see redirects below).
- Bulk metadata is symmetric across locales: each locale's sheet stays at its own path, and the platform applies them only when all 14 are listed in the site configuration (`POST https://admin.hlx.page/config/{org}/sites/{site}/metadata.json` with `{"source": ["/en/metadata.json", "/de-de/metadata.json", ...]}`). Until then, no bulk metadata applies; each sheet's URL patterns must start with its locale (e.g. `/de-de/**`).
- Redirects are per locale (`/{locale}/redirects.json`, by the user's choice). The platform only applies a root `/redirects.json` and there's no setting for more, so these sheets aren't applied automatically: redirects, including `/` → `/en/`, need another mechanism (e.g. CDN rules reading them).
- The query index (`helix-query.yaml`) excludes each locale's references, error pages, data and nav / footer (and, as a safeguard, block libraries and templates), and indexes the metadata columns (pageType, contentType, authorId, publishDate, readingTime, thumbnailImage, featuredImage, author, featured, priority (featureCard, featuredPriority as fallbacks), cardTitle, cardDescription, cardImage, cardImageAlt, imageAlt, eyebrow, category, hideInNav, region, country, language, persona, ...).
- Page properties are Title, Description, Keywords, Page Type, Navigation, Footer and 404 Page (Navigation, Footer and 404 Page are inherited by child pages); everything else page-level is a metadata sheet column. Page-specific values that aren't metadata (CTAs, author image overrides, share / download) are block fields. Don't hard-code user-facing strings in blocks; use placeholders.

### Three-Phase Page Loading

Pages are progressively loaded in three phases to maximize performance. This process begins when `loadPage` from scripts.js is called.

* Eager - load only what is required to get to LCP. This generally includes decorating the overall page content to create sections, blocks, buttons, etc. and loading the first section of the page.
* Lazy - load all other page content, including the header and footer.
* Delayed - load things that can be safely loaded later here and incur a performance penalty when loaded earlier

## Deployment

### Environments

Your local development server at `http://localhost:3000` serves code from your local working copy (even uncommitted code) and content that has been previewed by authors. You can access this at any time when the development server is running.

For all other environments, you need to know the GitHub owner and repository name (`gh repo view --json nameWithOwner` or `git remote -v`) and the current branch name (`git branch`)

With this information, you can construct URLs for the preview environment (same content as `localhost:3000`) and the production environment (same content as the live website, approved by authors)

- **Production Preview**: `https://main--{repo}--{owner}.aem.page/`
- **Production Live**: `https://main--{repo}--{owner}.aem.live/`
- **Feature Preview**: `https://{branch}--{repo}--{owner}.aem.page/`

### Publishing Process
1. Push changes to a feature branch
2. AEM Code Sync automatically processes changes making them available on feature preview environment for that branch
3. Run a PageSpeed Insights check at https://developers.google.com/speed/pagespeed/insights/?url=YOUR_URL against the feature preview URL and fix any issues. Target a score of 100
4. Open a pull request to merge changes to `main`
   1. in the PR description, include a link to `https://{branch}--{repo}--{owner}.aem.page/{path}` with a path to a file that illustrates the change you've made. This is the same path you have been testing with locally. WITHOUT THIS YOUR PR WILL BE REJECTED
   2. If an existing page to demonstrate your changes doesn't exist, create test content as a static html file and ask the user for help copying it to a cms content page you can link in the PR
5. use `gh pr checks` to verify the status of code synchronization, linting, and performance tests
6. A human reviewer will review the code, inspect the provided URL and merge the PR
7. AEM Code Sync updates the main branch for production
